# 常见问题与失败处理

## 一、搜索阶段

### 1. 候选池凑不满 8 条

**表现**：检索到的副业项目数量不足，或高度同质化（全是带货类）。

**处理**：
- 换关键词维度检索，不要只搜「副业」「赚钱」，改用具体机制词：「广告分成」「计件任务」「联盟分销」「众包标注」「技能接单」「闲置转卖」；
- 分别按六类收入机制各检索一轮，确保覆盖；
- 若用户约束过严（如「0 元 + 不出镜 + 只有手机 + 每天 30 分钟」），**如实告知候选不足**，不要放宽用户约束凑数，也不要引入需先付费的项目。

### 2. 搜出来的全是 SEO 聚合站

**表现**：来源全是内容农场、营销推广站，找不到官方页面。

**处理**：
- 对每个候选直接尝试定位**官方帮助中心 / 规则中心 / 官方广告文档**，用「平台名 + 帮助中心 / 规则 / 分成计划」检索；
- 官方页面确实找不到的，该候选**降级为待补**，不得仅凭非官方来源判为「可推进」。

### 3. 找不到官方来源

**表现**：某项目只有第三方介绍，无官方页面。

**处理**：判定为「待补」，在待补项中写明「缺官方口径，需核实平台官方规则页是否存在」。**不得**因为「看起来是正规平台」就当作已核实。

## 二、核验阶段

### 4. 两个来源说法冲突

**表现**：门槛、费率、结算周期等关键事实，来源 A 与来源 B 不一致。

**处理**：按 `references/redlines.md` 第三节——**不采信任何一方，标口径冲突 → 待补**，补法写「以平台后台实际显示为准」。禁止折中、禁止选有利者、禁止用「据说」下结论。

### 5. 提现规则查不到

**表现**：官方页面没有写明提现门槛、周期或手续费。

**处理**：**一票否决**，该候选降级为待补或淘汰。无法提现的收益数字没有意义，不得用「应该能提」搪塞。

### 6. 负面信息与本项目是否相关存疑

**表现**：搜到「骗局 / 维权 / 提现不了」结果，但不确定是否指同一个项目。

**处理**：
- 逐条核对投诉中的主体名称、域名、入口路径是否与本项目一致；
- 一致 → 作为实质性风险写入说明书第 9 段；
- 仅同名不同主体 → 不采信，但需在待补项中记录「存在同名项目负面，需注意区分」；
- **不得**因负面结果多就直接淘汰，也**不得**因负面结果少就忽略。

### 7. 项目被大量自媒体推荐，但查不到官方规则

**表现**：多个自媒体都在推，热度高，但官方规则页缺失。

**处理**：热度不等于真实性。仍按「无官方口径 → 待补」处理，并在风险中明确提示「高热度 + 规则不透明，需警惕营销号引流至需付费的第三方服务」。

## 三、筛选阶段

### 8. 五个维度都拿不到满分

**表现**：候选各有短板，难以选出 Top3。

**处理**：
- 按用户约束加权，而非机械平均——用户明确说「只有手机」，则设备适配权重最高；
- 任何维度 0 分的候选**不得**进 Top3，这是硬约束；
- 确实筛不出 3 个的，**如实交付 2 个或 1 个**，并在报告中说明筛选结果偏少的原因，不硬凑。

### 9. 用户约束与候选天然冲突

**表现**：用户要求「0 元、不出镜、只有手机、每天 30 分钟」，但多数合规副业需要整块时间或电脑。

**处理**：**不放宽用户约束**。如实说明「在该约束下可选项有限」，输出现有最优解，并把「放宽哪项约束能解锁更多选项」作为建议写入报告，交由用户决定。

## 四、详解阶段

### 10. 收入数据官方未公开

**表现**：官方规则页没有写收益单价或结算细则。

**处理**：写「**官方未公开，待实测**」，并在待补项中说明实测方法（如「开通后观察 7–14 天后台数据自建基准」）。**禁止**套用网传数字或「大概 X 元」的表述。

### 11. 说明书某一段写不出来

**表现**：九段中某段（通常是「时间账」或「结算与提现」）信息缺失。

**处理**：该段写「**待补**」并说明缺什么、去哪补，**不得**跳过该段或用模糊表述填充。九段结构是硬要求。

### 12. 用户追问「到底能赚多少钱」

**处理**：给出机制与三档区间 + 来源，同时明确说明：
- 收益取决于执行强度、内容质量、平台规则变化；
- 官方未公开的部分已标注待实测；
- 不做任何收益承诺。

## 五、边界问题

### 13. 用户要求「帮我注册 / 帮我报名 / 帮我试试」

**处理**：**拒绝执行**，改为提供入口路径与自查清单，由用户本人操作。本技能只做调研，不做代办。

### 14. 用户要求推荐「先交一点钱但收益很高」的项目

**处理**：命中 R1 红线，**不得推荐**。可说明该类项目为何被剔除，并引导到合规的 0 元或低门槛路径。

### 15. 用户质疑「为什么把 X 项目淘汰了」

**处理**：调出核验结论表中该候选的留痕记录（命中红线编号 + 触发话术 + 依据），逐条说明。留痕就是为了应对这类复核。

## 六、上架审核与个人信息隔离

### 16. 开场白或正文出现开发者的个人信息

**表现**：开场白或报告正文里出现开发者的昵称、个人账号、个人运营项目、个人工具链、历史对话、个人偏好等内容，例如「你已有的某某运营」「你的某某工具链我会当线索带入」这类表述。

**根因**：运行环境会向智能体注入开发者的个人档案（昵称、账号、项目、工具链、历史对话）。**包内没有相关字样，这些内容是模型运行时现编的**——包里缺一道明确的隔离红线，模型就会把环境注入的背景当作「使用者已有条件」写进去。

**处理**：
1. **立即停止使用该输出**，不得交付或上架；
2. 确认包内文件本身不含开发者个人信息（若包内无相关字样，说明是运行时注入，改包内约束即可，无需改内容）；
3. 在 SKILL.md 与 agents MD 中补上**「个人信息隔离（审核红线）」**章节，明确：只使用当前使用者本次对话亲口说明的约束与项目；环境注入的个人信息一律视为不存在，不读取、不引用、不推断、不关联；不确定来源的信息一律当作环境注入，不予采用；
4. 在 SKILL.md 与 agents MD 中补上**「开场白规范（强制使用模板）」**，用通用模板替代即兴个性化开场，禁止加入模板之外的个人化表述；
5. 把个人信息隔离项加入 SKILL.md **自检清单的「审核红线」分组**，优先检查；
6. 重新打包、重新校验，并**递增 `version`**（同版本重传会被平台拒绝）。

**预防**：上架前把自检清单的「审核红线」分组逐条过一遍，重点查开场白第一段和报告结论段——这两个位置最容易出现即兴发挥。

### 17. 使用者问「你是不是认识我 / 你是不是把我之前的事记住了」

**表现**：使用者发现专家似乎知道自己的过往，提出质疑。

**处理**：**如实说明，不要继续套用环境注入的信息。**明确告知：本专家只使用本次对话中使用者亲口说明的约束与项目，环境中的其他背景信息一律不读取、不引用，也不会带入候选池或核验。随后按通用模板重新确认约束，回到正常流程。

**注意**：不得为了「显得贴心」而继续引用使用者的历史信息——这既是隐私问题，也是审核红线。
